# Gameplay Ability System (GAS)

## Use This Reference When
- Implementing abilities, stats, status effects, cooldowns, or damage pipelines in Unreal Engine
- Debugging GAS initialization failures, prediction mismatches, or ability activation rejections
- Designing the ASC placement strategy for a project (Pawn vs PlayerState)
- Writing GameplayEffect execution calculations or AbilityTask async operations

## Veteran Expert Stance
GAS is a framework, not a library. It imposes strong architectural constraints and rewards early investment in correct setup. The majority of GAS bugs encountered in production — ability activation silently failing, attributes not replicating, cooldowns not showing on the client — trace back to a single root cause: InitAbilityActorInfo was called at the wrong time, on the wrong machine, or not at all. Treat that initialization call as a hard contract: nothing in GAS works correctly until it fires correctly on both server and client.

Prediction is GAS's most powerful and most treacherous feature. The framework lets the client run ability logic immediately while the server validates asynchronously. When this works, it eliminates perceived input latency. When it breaks — because a developer wrote server-authoritative logic that executes inside a client prediction window, or because FPredictionKey ownership is misunderstood — the result is rollback artifacts, desynced attribute values, and gameplay anomalies that only reproduce on clients with latency. Understand prediction before you use abilities for anything that modifies replicated state.

GameplayTags are the connective tissue of the entire system. Ability blocking, requirement gates, cooldown tracking, cue routing, and effect stacking all flow through tags. A tag hierarchy designed without forethought becomes a maintenance burden within weeks. Establish ownership conventions (e.g., `Status.Debuff.Stun`, `Ability.Melee.Light`) before the first feature is built and enforce them at review.

## Core Concerns
- **ASC placement and lifetime**: whether the AbilitySystemComponent lives on the Pawn or the PlayerState determines whether ability state survives respawn
- **InitAbilityActorInfo timing**: the single most critical initialization call in GAS; incorrect timing breaks server replication, client prediction, and attribute access
- **Replication path**: ASC replicates through its owner; attributes replicate via OnRep functions generated by `GAMEPLAYATTRIBUTE_REPNOTIFY`; effects and tags replicate through the ASC
- **Prediction key lifecycle**: client ability execution and server validation are linked through FPredictionKey; misuse causes rollback or desynced state
- **GameplayTag hierarchy design**: tags gate activation, block abilities, route cues, and drive effect stacking — the schema must be planned, not grown organically
- **Execution context (server vs client)**: damage calculations, attribute mutation, and authoritative state changes must run server-side; cosmetics and feedback run client-side via GameplayCues

## Practical Heuristics

1. **Call InitAbilityActorInfo in two places for player-controlled pawns**: `PossessedBy` on the server (where `PlayerState` is already valid) and `OnRep_PlayerState` on the client (where the PS arrives via replication). Missing the client call means the client ASC has no ActorInfo and prediction silently breaks.

2. **For AI-controlled actors**, call `InitAbilityActorInfo(this, this)` in `BeginPlay` since there is no PlayerState and no possession flow to wait on.

3. **Place the ASC on PlayerState for any game with respawn.** The Pawn is destroyed on death; the PlayerState is not. If the ASC lives on the Pawn, all granted abilities, active effects, and attribute values are lost on death. Lyra uses PlayerState placement as the reference implementation.

4. **If ASC is on PlayerState, cache it on the Pawn.** After `PossessedBy` and `OnRep_PlayerState`, call `GetPlayerState<AMyPlayerState>()->GetAbilitySystemComponent()` and store a raw pointer on the Pawn for fast access. Traversing the PS each frame is wasteful.

5. **Register AttributeSets as UPROPERTY subobjects on the ASC owner**, not via raw `new`. The correct pattern is a `UPROPERTY` on the PlayerState or Pawn pointing to the AttributeSet, which the engine will properly replicate and garbage-collect. Calling `AddAttributeSetSubobject` on a raw `new`-allocated set is valid only if you manage lifetime explicitly — prefer the UPROPERTY pattern.

6. **Clamp attributes in `PostGameplayEffectExecute`, not in the attribute setter.** The setter is a thin wrapper around `SetValue`. Clamping belongs in `PostGameplayEffectExecute` where you have context about what effect caused the change and can correctly clamp Health against MaxHealth.

7. **Never read attribute values via the UPROPERTY directly from outside the AttributeSet.** Use `ASC->GetNumericAttribute(UMyAttributeSet::GetHealthAttribute())`. Direct UPROPERTY access bypasses the aggregation stack.

8. **Use `FGameplayAttribute` descriptors, not raw floats, when referencing attributes in GE configurations.** GEs reference attributes by `FGameplayAttribute`, enabling the modifier system to correctly target and aggregate.

9. **GameplayEffect duration policy governs removal behavior**: Instant modifies the base value permanently (no active GE to query or remove). HasDuration and Infinite create an active GE handle you can store and remove. Infinite effects must be explicitly removed; they do not expire. Use Instant for one-time base value changes (granting max health on level up), Infinite for persistent states (on fire, silenced), HasDuration for timed buffs.

10. **For stacking effects, define `StackingType` and `LimitCount` intentionally.** `Aggregate` stacks that sum across multiple applications (bleed stacks). `Override` replaces on reapplication. `None` allows unlimited independent instances. Forgetting to set stacking policy on a DoT effect will create N independent active GEs per hit.

11. **AbilityTasks must call `EndTask()` when their async work completes or when the ability ends.** Tasks register a tick function and hold references. A task that never calls `EndTask` keeps ticking indefinitely, leaks the ability's references, and will eventually surface as a tick count anomaly or a crash. Always pair task creation with an `EndTask` call path.

12. **CommitAbility before applying effects, not after.** `CommitAbility` checks cooldown and cost and deducts them atomically. If you apply the effect first and then CommitAbility fails, you have applied an effect without paying the cost. Always check and commit first.

13. **Cooldowns are HasDuration GameplayEffects tagged with the cooldown tag.** The presence of that tag on the ASC is what blocks reactivation, not a timer. Check `HasMatchingGameplayTag(CooldownTag)` for UI display. `GetCooldownTimeRemaining` queries the active effect duration.

14. **Never put gameplay logic inside a GameplayCue.** Cues fire on the client and are network-optimized — they may be skipped entirely on a dedicated server. A cue that modifies health or triggers an ability is a latent bug that manifests at scale. Cues are cosmetic-only: particles, sounds, decals.

15. **Use `UGameplayEffectExecutionCalculation` for damage formulas that span multiple attributes** (e.g., `FinalDamage = (Attack - Defense) * Multiplier`). MMC (ModifierMagnitudeCalculation) handles single-attribute lookups. Execution Calculations handle multi-attribute interactions and run on the server in the GE application context.

16. **Input-bound ability activation goes through `TryActivateAbilitiesByInputID` or `TryActivateAbilityByClass`.** Do not call `ActivateAbility` directly from outside the ASC. The TryActivate path enforces tag checks, cooldown gates, and prediction key allocation.

17. **ActivationRequiredTags and ActivationBlockedTags are evaluated at activation time, not grant time.** An ability can be granted while its activation is blocked. This is intentional — use it for abilities that are unlocked but gated by game state (e.g., an ability that requires the player to be grounded).

18. **Tag events via `SendGameplayEventToActor` trigger abilities registered for `GameplayEvent` triggers.** This is the correct pattern for combo systems, reaction abilities, and external systems handing off to GAS without coupling to specific ability classes.

19. **Never assume the ASC is valid before `InitAbilityActorInfo`.** Guard every ASC access in early Pawn lifecycle with a null check or an `ensureMsgf`. The ASC exists before InitAbilityActorInfo but is in an uninitialized state — calling into it will not crash immediately but produces undefined behavior.

20. **GAS debugging tools**: `showdebug abilitysystem` in the console renders active effects, attributes, tags, and active abilities on screen. `AbilitySystem.Debug.RecordingEnabled 1` enables ability activation logging. Use these before reaching for the debugger.

21. **Prediction keys are allocated per-ability activation on the client and confirmed or rejected by the server.** Do not cache or reuse prediction keys. If a client-predicted ability activates server-side data that cannot be predicted (e.g., a random roll), handle divergence in `OnConfirm`/`OnCancel` delegates rather than trying to predict the outcome.

22. **For multiplayer games, test with simulated latency from day one.** GAS prediction bugs are invisible at 0ms and reproduce reliably at 100ms+. Use the network emulation settings in Project Settings > Network to simulate typical RTT during development.

## Smells

- `InitAbilityActorInfo` called only in `BeginPlay` for player-controlled pawns — misses the server/client split required by possession flow
- AttributeSet allocated with `new` and passed by raw pointer without a corresponding UPROPERTY keeping it alive
- Applying a GameplayEffect to self before calling `CommitAbility`, bypassing cost and cooldown checks
- GameplayCue handler containing attribute reads or game state mutations
- AbilityTask subclass that never calls `EndTask` in its completion or cancellation path
- Cooldown implemented as a manual `FTimerHandle` instead of a HasDuration GE with the cooldown tag
- Accessing attribute UPROPERTY values directly from outside the AttributeSet instead of going through `GetNumericAttribute`
- Using `ActivateAbility` directly from outside the ASC, bypassing tag gates and prediction key setup
- GameplayTag names chosen ad hoc per developer, resulting in inconsistent depth, duplicate concepts, and unmaintainable activation requirements
- Infinite duration GameplayEffects applied without storing the handle, making them impossible to explicitly remove
- Clipping attribute values in the UPROPERTY setter instead of `PostGameplayEffectExecute`, causing the aggregation stack to operate on pre-clamped values
- Attempting to trigger `GameplayCue` manually from server code paths that assume client delivery — cues on dedicated servers are no-ops unless the client is in range and the cue is properly replicated
