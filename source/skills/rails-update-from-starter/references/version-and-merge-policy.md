# Baseline and Merge Policy

## Three-way inputs

Let B be the exact previous framework baseline, S the current framework rendered with recorded adopted inputs, and P the current project bytes. The generator manifest retains B and content hashes; source Git revision without dirty-content hashes is insufficient.

| Relationship | Disposition |
| --- | --- |
| S equals B | Preserve P, including intentional project deletion. |
| P equals B | Accept S after preview. |
| P equals S | Accept the shared result. |
| S and P changed disjoint portions of B | Merge with project edits retained; verify the diff and checks. |
| Overlap, unprovable baseline, concurrent creation, or deletion versus changed source | Preserve P and report conflict; no automatic overwrite. |

A new baseline records S, not the merged P. Otherwise later updates misclassify project edits as framework ownership. Validate hashes/schema and reject malformed manifests or linked paths. Retired source files remain preserved in the project.

## Without a baseline

Create a separate generated review fixture with explicit selected profile, host, and concrete identity. Compare useful commands, routing, and constraints against maintained project files. Keep unproven project content project-owned. A manual partial adoption cannot silently create a valid full-generator manifest. Recover old source from demonstrable history only when it exactly identifies generated bytes and inputs.

## Version separation

`metadata.version` is a local document version where that schema is adopted. `agentic_rails_source_version` is an optional provenance label on actually derived files; it is not a merge base. Preserve the old label on conflict and advance only for verified reconciliation. Do not add a fabricated `0.0` baseline. Product versions and published identity are independent and remain unchanged.

## Profile and structure migration

Preserve current profile on ordinary update. A requested change previews generated content separately; do not bypass refusal of changed generation inputs. Explicit structural migrations retain exact dirty bytes, map old links/status/acceptance into new destinations, verify content, and leave original history intact by default. Neither migration nor cleanup requires a commit; use a scoped recovery snapshot and honor commit authority.

Current generator ordinary errors roll back applied file content, but an abrupt process crash can interrupt a multi-file update. Recovery must compare saved bytes, manifest, and current content before replaying. Do not describe a per-file atomic write as an atomic tree transaction.
