# Blocker handling

Inspect the actual error and surrounding implementation. Try a supported
alternative when evidence warrants it. For a genuine unresolved question, invoke
`rails-spike` by name with one question and a bounded experiment. For tangled
work, use natural-seam decomposition rather than changing product requirements.

After two attempts without new evidence, change the approach or record the
blocker. A partial outcome is useful evidence but does not make the whole item
complete. Select independent work already in the authorized queue; do not create
an unlimited investigation or planning backlog to avoid a legitimate stop.

Preserve user-owned dirty work and failed experiment evidence. Strategic changes
to architecture, product scope, or protected files require existing or new user
authority. A run can end when its bound is reached, work is finished, the user
stops it, or no authorized item can progress. Record the actual reason and next
action; no mandatory stopping questionnaire is needed.
